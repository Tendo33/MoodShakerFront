# Internationalization

Covers locale resolution and dictionary access. Read before touching `proxy.ts`,
`app/layout.tsx`, `context/LanguageContext.tsx`, or anything under `locales/`.

## The URL Prefix Is The Only Answer

Language used to be resolved independently in three places, each with its own
fallback chain, so they could disagree — the proxy could redirect to `/cn` from a
cookie while the layout read `accept-language: en` and rendered
`<html lang="en">`.

| Component | Reads |
| --- | --- |
| `proxy.ts` | The prefix. Only when absent: cookie, then `accept-language`, then default |
| `app/layout.tsx` | The `x-moodshaker-locale` header the proxy forwarded |
| `context/LanguageContext.tsx` | `usePathname()` |

Rules:

- `lib/i18n/config.ts` is the only source for `LOCALES`, `DEFAULT_LOCALE`, the
  cookie and header names, and the four resolution helpers.
- Only the proxy may derive a locale from something other than the URL. Anywhere
  else, read the prefix.
- Never resolve language from `localStorage` or `navigator.language`. State that
  can drift from the address bar is what let `/en/gallery` render Chinese.
- Persist the explicit choice as a **cookie**, not `localStorage`. The proxy runs
  before any client code and can only read cookies. The two were once the same key
  name in different stores, which made the proxy's cookie branch dead code and
  silently discarded the user's choice on every unprefixed URL.
- Do not write the cookie for a locale inferred from `accept-language`. Freezing a
  guess into an explicit-looking preference makes it outrank the header it came
  from.

`<html lang>` stays in `app/layout.tsx`: only one layout may render `<html>`, and
`app/page.tsx` and `app/not-found.tsx` live outside the `[lang]` segment. Use the
BCP 47 tag from `HTML_LANG` in `lib/i18n/config.ts` (`zh-CN`, not `cn`).

That layout alone is not sufficient. It is a server component, so it does not re-render
on a client-side navigation and the attribute stays at its first-load value — switching
/cn to /en changed the URL and the copy while `lang` remained `zh-CN`. `LanguageContext`
syncs it in an effect for that reason; keep both, and keep the tag map shared so they
cannot drift.

The cost of a stale `lang` is larger than the markup: every `html:lang(en)` rule in
`globals.css` stops matching, so English headings lose `overflow-wrap: break-word` and
long words get clipped, and screen readers keep reading English with Chinese
pronunciation. A hard reload looks correct, so this only shows up when clicking through
the selector — see "Real-Browser Checks" in `quality.md`.

`availableLanguages` from the context is the array `["cn", "en"]`. Map over it. A
previous version called `Object.entries` on it and got `[["0", "cn"], ["1", "en"]]`,
which routed to `/1/questions` and broke switching entirely.

## Accept-Language

Parse by quality value. Do not use `header.startsWith("en") ? "en" : "cn"` — that
turned `fr,en;q=0.9` into Chinese even though English was acceptable and Chinese
was not listed. `q=0` means refused, `*` means the default, and every Chinese
variant maps to the one Chinese dictionary. Return `null` when nothing is
acceptable and let the caller decide.

## Dictionaries

Keys are flat and dotted. Do not convert them to nested objects: 16 keys are both
a leaf and a prefix (`spirits.gin` alongside `spirits.gin.description`), and one
name cannot be both a string and an object.

`cn` is the reference. `lib/i18n/dictionary.ts` locks `en` to exactly its key set
in both directions — a missing key and an extra key each fail the build. Do not
type a dictionary as `Record<string, string>`, and do not type keys as
`keyof cn | keyof en`: a union accepts a key present in only one language, which
is the drift the type is supposed to prevent.

### `t()` versus `tDynamic()`

- `t(key: TranslationKey)` takes literal keys. A typo fails the build.
- `tDynamic(key: string): string | null` is for keys assembled from data. Unknown
  keys return `null` so the caller chooses a fallback.

Never widen `t()` back to `(key: string) => string`. That signature returned the
key when it was missing, so `detail.alternative` — absent from both dictionaries —
rendered as visible text on the detail page for as long as it existed.

Look keys up with `hasOwnProperty` and check the value is a string. Plain indexing
resolves `toString` to `Object.prototype.toString` and hands a function to a
caller expecting text.

## Known Gap

`app/[lang]/gallery/GalleryContent.tsx` holds its own hardcoded spirit, alcohol,
and flavour arrays, and sends them as API query parameters. They are narrower than
`lib/domain/vocabulary.ts`, so cocktails with `alcoholLevel: "none"` or a `floral`
profile cannot be filtered. Unifying them changes the API filter contract and
belongs with the data-model work.
